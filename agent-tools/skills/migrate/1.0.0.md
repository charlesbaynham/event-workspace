# Migration to 1.0.0 — memory filed by a nightly pass, notes with frontmatter

**From:** any 0.x workspace. **Safe to re-run:** yes; each step checks before
it changes anything.

What changed in how memory is stored:

- every note in `memory/notes/` carries frontmatter (`name`, `description`,
  `aliases`, `updated`), and `memory-check.sh` indexes it at session start;
- sensitive lines are kept and tagged `[sensitive]`;
- the digest is the core only, 500 words or fewer not counting Tools &
  resources;
- `memory/filing-state.md` records each filing pass;
- the log is filed by a nightly scheduled task (the `memory-compact` skill),
  not by a compaction when it passes 40 entries.

`memory.py` below means `python3 agent-tools/skills/memory-compact/memory.py`,
run from the repository root.

## 1. Skill links

Skills reach Claude Code through `.claude/skills/<name>` symlinks, and Codex
through `.agents/skills/<name>/SKILL.md` stubs. Both are written at birth, so a
skill added later needs its entry made by hand. For every directory under
`agent-tools/skills/`, make sure that:

- `.claude/skills/<name>` exists, as a relative symlink
  `../../agent-tools/skills/<name>`;
- if `.agents/skills/` exists, `.agents/skills/<name>/SKILL.md` exists,
  copying the shape of the stubs already there.

For 1.0.0 that means `migrate` and `setup` are the new ones. `update.sh` from 1.0.0 onwards
does this itself.

## 2. The state file

If `memory/filing-state.md` is missing, create it:

```
# Memory filing state

<!--
Written by the memory-compact skill's filing pass, and by nothing else.
last_run is when the last pass started gathering: the next pass reads the
sessions, commits and log entries that came after it. retry lists sessions
whose review failed and must be read next time. migrated lists the major-
version migrations this memory has been through; a workspace born on a major
already has that major's structure. Git history keeps the earlier values.
-->

last_run: never
last_commit: none
last_sessions: 0
retry:
migrated:
```

If it exists without a `migrated:` line, add one, empty.

## 3. Refresh the inherited header comments

`memory/log.md` and `memory/user-edits.md` were seeded at birth, and their
header comments still describe compaction into the digest. Replace each
file's first `<!-- … -->` comment, and only that (no entries, no other
lines), with the 1.0.0 text below. Skip a file whose header already matches.

`memory/log.md`:

```
<!--
Sessions APPEND terse observations here — never edit or reorder existing
lines — when a transcript won't carry them: unattended sessions (scheduled
tasks, webhook wakes), sessions the nightly pass can't list (local CLI, Codex,
a co-user's own account), and anything settled only inside tool work. The
memory-compact skill's filing pass files these into memory/notes/ and the
digest, then removes exactly the lines it filed. Git history preserves
everything.

Format, one observation per line:

- [YYYY-MM-DD] TYPE: observation

TYPE is one of:
  DECISION  — a choice was made (record the choice AND the reason)
  STATE     — something changed: built, fixed, broke, merged, deployed
  LEARNED   — a fact worth not re-discovering (gotcha, quirk, preference)
  OPEN      — a question raised or task deferred
  RESOURCE  — an ID, path, URL, or environment fact worth keeping
  CORRECTION— something previously believed/recorded is wrong

Rules for writers:
- One line each, written at the moment the thing happens — not batched at the end
  (sessions die without warning; unlogged observations are lost).
- Provenance matters: "User decided X" vs "I suggested X (not yet confirmed)".
  Never log your own suggestion as the user's decision.
- Never log secrets, tokens, or credentials.
- Hypotheticals stay marked as hypothetical.
-->
```

`memory/user-edits.md`:

```
<!--
Numbered list of the owner's corrections and exclusions. They CONSTRAIN what
any session and the nightly filing pass may write into memory/notes/ and
digest.md. Modified only on the owner's explicit request. Semantics: a factual
override wins over notes, log and transcripts; an "Exclude ..." subject is
removed and never re-filed, even from older transcripts; max ~30 entries;
confirm before removing or replacing one. Never store secrets or standing
instructions (those belong in EVENT.md).
-->
```

## 4. Restructure the stored memory: the first filing pass

Run the `memory-compact` skill's pass now, by hand ("Running the pass").
Because `last_run` is `never`, it is the workspace's **first pass**, and
`filing.md` then:

- adds frontmatter to **every** note;
- tags existing sensitive content in **every** note, not only the ones it
  edits: `sensitive: true` in the frontmatter of a note that is mostly guests'
  private details, `[sensitive]` on the lines elsewhere (remove nothing that was
  kept before; tag it);
- rewrites the digest to its new size, moving anything only the digest held
  into the right note first;
- files the pending log entries and the sessions since the last compaction.

Let it commit as it normally does (`memory: nightly filing …`).

After it, `memory.py check` must exit 0. Warnings about long notes are
expected: they are split gradually by later passes.

## 5. The scheduled task

The old nightly compaction task only ran when the log passed 40 entries, and
its prompt describes the old procedure. Run the **`setup` skill** (registered
in step 1; or read `agent-tools/skills/setup/SKILL.md`). It audits every
automation the workspace needs. It **updates the old task in place** (prompt,
name, schedule), keeping its history, and asks the owner which model should
run it. It proves the task with one run, checks the WhatsApp wake if the
workspace has one, and records the ids in `memory/notes/automations.md`.

If this session can't reach the scheduling tools, the skill walks the owner
through the browser instead. Until the task is replaced, nothing reads the
sessions' transcripts.

If the old task can't be converted in place (it resumes a fixed session
instead of starting a fresh one each night, which `update_trigger` can't
change), the setup skill creates a new task and asks the owner before
disabling the old one. It never deletes the old one.

## 6. Record and commit

Add `1.0.0` to the `migrated:` line of `memory/filing-state.md`
(comma-separated if others are there), then
`agent-tools/sync-push.sh "migrate: 1.0.0 — notes indexed, sensitive lines tagged, nightly pass"`.

Report: notes given frontmatter, notes and lines marked sensitive, the digest's
size before and after, the scheduled task's id and model, and whatever the
filing pass handed to the owner.
